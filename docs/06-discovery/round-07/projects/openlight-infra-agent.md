**Уникальность:** Проект вырос из «бота для Raspberry Pi» в **агент для личной инфраструктуры с Telegram как интерфейсом**. Ключевой вывод после 2 месяцев разработки: LLM не должен иметь прямых прав — он выбирает из набора **предопределённых skills**, safety на уровне Go-кода внутри skills, не на уровне промпта.

## Архитектурная эволюция

```
v0.0.1: reactive bot — ты спрашиваешь, агент отвечает
v0.1.0: monitoring loop — агент сам наблюдает и уведомляет
```

Telegram как интерфейс: кнопка «Restart» в алерте вызывает тот же `service_restart`, что и ручная команда.

## Ключевой архитектурный принцип

> «Инфраструктуре не нужен автономный агент —  
>  ей нужен понятный, верифицируемый путь выполнения.  
>  LLM может только выбирать из готовых skills,  
>  сами skills обеспечивают безопасность на уровне Go-кода.»

Это прямой ответ на проблему «AI-агент на OpenClaw слил $441К» (R07): не промпт-инжиниринг, а архитектурное ограничение прав агента.

## Почему важно для Svyazi

Lorenzo запускает `improve_*.py` через `run_improve` — это уже паттерн «LLM выбирает skill».  
openLight формализует это как архитектурный принцип безопасности:  
**агент не пишет команды, агент выбирает из каталога** → risk surface минимален.

Применимо к `improve_watcher.py` (Ступень 6) — автономный агент должен работать только через зарегистрированные скрипты.

## Возможные комбинации

| Комбинация | Новое свойство |
|------------|----------------|
| **openLight принцип + Lorenzo watcher** | Ступень 6 безопасна: агент выбирает из improve_*.py, не пишет шелл |
| **openLight + Self-Aware MCP (R04)** | Temporal context + safe skill execution — production-ready автономия |
| **openLight + Memory MCP v2 (R06)** | Skills + классификация артефактов → агент знает, что делал раньше |
| **openLight + TRAIL spec (R04)** | TRAIL между серверами, openLight принцип внутри каждого сервера |
