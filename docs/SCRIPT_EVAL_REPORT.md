## 5. Плюсы реализации

### ✅ 1. Композируемость
Скрипты работают как UNIX-утилиты — каждый делает одно. Рецепты их компонуют.
`--run weekly-full` = 9 скриптов в правильном порядке автоматически.

### ✅ 2. Dry-run везде
Критическое улучшение: `--dry-run` теперь реально запускает скрипт с флагом,
а не просто пропускает. Можно безопасно тестировать любую цепочку.

### ✅ 3. CardEnvelope — общий язык данных
Любой документ превращается в `CardEnvelope` с единым форматом:
`card_id`, `card_type`, `state`, `edges`, `payload`. Это основа для
интеграции Yodoca, AgentFS, CardIndex (план PROTOTYPE_SPEC.md).

### ✅ 4. Трёхуровневый поиск
- Файловый (search_index.json, 2205 записей)
- Абзацный (passages.json, 10 407 абзацев — BM25 с k1=1.5, b=0.75)
- Живой (19 856 абзацев из 1704 файлов без предварительного индекса)

### ✅ 5. История и телеметрия
`recipe_history.json` логирует каждый запуск: рецепт, время, скрипты, результаты.
`improve_benchmark.py` замеряет производительность. `audit.db` — SQLite лог событий.

### ✅ 6. Самодокументированность
`improve_self.py --audit` показывает состояние всей системы:
0 скриптов без docstring, все 159 имеют `if __name__ == '__main__'`.

### ✅ 7. Offline-first
Всё работает без интернета и без LLM. BM25, граф, карточки — локально.
LLM-скрипты (`improve_llm_*.py`) — опциональны, требуют `ANTHROPIC_API_KEY`.

### ✅ 8. Масштаб
1 741 документ, 987 000 слов, 1 623 потенциальных карточки.
Система не замедляется — BM25-поиск по 19 000 абзацев за 2с на обычном CPU.

## 6. Минусы и ограничения

### ⚠️ 1. 137 из 159 скриптов без --dry-run
Контентные скрипты (`improve_abstract.py`, `improve_auto_toc.py` и др.)
не имеют `--dry-run` флага. Запуск через рецепт может изменить файлы без предупреждения.

**Что делать:** добавить `--dry-run` в `NO_DRY_RUN` список рецепта,
или добавить флаг в сами скрипты через `improve_self.py --batch`.

### ⚠️ 2. CardStore — только 7 карточек из 1623 возможных
`cards/` заполнен только для `05-habr-projects`. Полный build займёт минуты
и потребует ~1 ГБ памяти. Нет инкрементального обновления.

**Что делать:** добавить `--incremental` в `cmd_build()` — обновлять только
изменённые файлы (сравнивать `updated_at` с mtime).

### ⚠️ 3. OSError на длинных путях в ссылках
`improve_broken_links.py` падает на документах с Markdown-ссылками > 255 символов.
Блокирует `quality-check` рецепт (1/6 скриптов fail).

**Что делать:** добавить `try/except OSError` с логированием в broken_links.py.

### ⚠️ 4. MCP-сервер требует установки
`pip install mcp` не входит в стандартный запуск. В CI и clean-env это блокирует.
Демо-режим частичный — 7 из 11 инструментов.

**Что делать:** добавить `mcp` в `requirements.txt`, добавить graceful fallback.

### ⚠️ 5. Recipe history — только 1 запись
История фиксирует только полные запуски через `--run`. Отдельные
`improve_*.py` вызовы не логируются. Нет агрегации по дате.

**Что делать:** добавить `--stats --since 7d` для истории за период.

### ⚠️ 6. Нет семантического поиска
BM25 — точный, но не понимает синонимы. «Агент с памятью» и «memory agent»
дадут разные результаты несмотря на одинаковый смысл.

**Что делать:** добавить hnswlib (MIT, без сервера) — уже запланировано
в PROTOTYPE_SPEC.md Итерация 1.

### ⚠️ 7. Типы карточек — только by filename
`_detect_card_type()` смотрит только на имя файла. `yodoca.md` → `project`,
но `docs/01-svyazi/07-mvp-planning.md` → `doc`, хотя содержит планирование.

**Что делать:** добавить анализ frontmatter `type:` и первого H1.

## 8. Итоговая оценка

### Что сработало отлично

1. **Рецептная система** — удобнее всего. Одна команда вместо пяти. Dry-run работает честно.
2. **CardEnvelope** — правильная абстракция. Даёт общий язык для всех компонентов Svyazi 2.0.
3. **Трёхуровневый поиск** — каждый уровень нужен для разных сценариев.
4. **improve_self.py** — самоаудит + кодогенерация = мощная пара.

### Что требует доработки

1. **137 скриптов без dry-run** — системная проблема, нужен пакетный фикс.
2. **CardStore не заполнен полностью** — 7 карточек вместо 1623.
3. **MCP зависимость** — нужен `requirements.txt`.

### Общее направление

Проект движется от **коллекции скриптов** к **Knowledge OS** — системе,
где документы имеют тип, состояние, рёбра и историю изменений.
Следующий большой шаг — заполнить CardStore и добавить семантический поиск
(Итерация 1 из PROTOTYPE_SPEC.md).
