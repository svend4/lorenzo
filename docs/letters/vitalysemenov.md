## Письмо

Здравствуйте!

Я строю Svyazi 2.0 — локальную knowledge-платформу для Claude. Ключевая задача —
дать агенту постоянную типизированную память, которая не зависит от внешних
сервисов и работает офлайн. Именно поэтому agent-memory-mcp для меня —
ближайший из рассмотренных проектов к тому, что нужно как memory-слой.

**Что уже решено у вас:**

Четыре типа записей (`episodic`, `semantic`, `procedural`, `working`) —
это точная типизация, которой не хватает большинству memory-систем.
В PROTOTYPE_SPEC Svyazi я использую похожее разделение: `fact`, `episode`,
`project`, `person` — но без явного `procedural` (как делать) vs `semantic`
(что есть). SQLite + WAL — тот же стек, что у CardStore Svyazi, прямая
совместимость.

Концепция Memory OS с gardener-loop и bi-temporal фактами — это ровно то,
чего не хватает базовому agent-memory-mcp и что я проектировал отдельно.

**Один технический вопрос:**

Как gardener-loop решает конфликты bi-temporal фактов? Конкретно: если
в `episodic` памяти есть запись «X произошло в момент T₁» (время события),
добавленная в момент T₂ (время записи), а потом приходит новая запись
«X не произошло, произошло Y» — что побеждает? Last-write-wins,
доверие к более поздней `event_time`, или есть явный механизм разрешения
конфликтов?

Этот вопрос критичен для Svyazi: агент должен уметь исправлять устаревшие
факты, не теряя историю.

**Что я готов предложить:**

- Описание того, как agent-memory-mcp + Memory OS закрывают memory-слой
  в архитектуре Svyazi 2.0 (задокументировано детально)
- Обсуждение, как `CardEnvelope` Svyazi соотносится с типами записей
  agent-memory-mcp — возможно, контракты уже совместимы
- Если интересно — пример интеграции через MCP: CardStore пишет в
  agent-memory-mcp, gardener читает и консолидирует
